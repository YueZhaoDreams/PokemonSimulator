## Instructions
# verify-gate

Independent **QA agent** workflow for epic acceptance gates. Use after the merged app is running when a gate is `ready_for_review` and before a human records the pass in `.harmonia/epics/<epic-slug>.json` `passed_gates`.

**Independence rule:** Do not treat implementation reasoning or prior slice sessions as proof. Read only the gate contract (`breakdown.json`), epic spec, and runtime signals (HTTP, filesystem, browser, pytest integration tests).

Invocation:
- `/verify-gate <epic-slug> <gate-id>`
- `/verify-gate docs/epics/<epic-slug>/spec.md <gate-id>`
- Parent orchestrators (`implement-epic-features`) invoke this at checkpoint steps for the blocking or exit gate.

Execution flow:
1. Read `docs/epics/<epic-slug>/breakdown.json`, locate `acceptance_gates[]` entry matching `<gate-id>`, and read `consumer`, `verifier`, and `verify` steps.
2. Read `docs/epics/<epic-slug>/spec.md` for context and non-goals. Read `.harmonia/epics/<epic-slug>.json` for adhoc notes.
3. Confirm the gate is `ready_for_review`. If `after_features` is `["__all__"]`, that means every slug in `breakdown.json` `features[]` is `done`. Otherwise every listed `after_features` child slice must be `done`. Stop if not ready.
4. Confirm **production is the verification environment** (this app at `http://127.0.0.1:8000`, or the LAN URL from `README.md`). Check out `main`, pull the merged commits from origin, then restart `./run.sh` / uvicorn so the process is serving the merged code — `run.sh` does not reload and serves whatever is currently checked out. Stop if the running app is not reachable or is still on pre-merge code.
5. **Run each `verify` step** and record pass/fail with evidence:
   - `consumer: agent` — prefer API calls, filesystem assertions, and targeted `pytest` integration tests over browser UI.
   - `consumer: human` — use browser MCP for smoke only; mark UX judgment items as `human-required` in the report even when technically smoke-passed.
   - `consumer: both` — run machine checks first, then browser smoke; split evidence per step.
6. Produce a **structured gate report** (markdown) with: gate id/title, consumer, verifier, per-step status, commands/URLs used, failures, screenshots when browser was used, and overall recommendation.
7. Persist the report under `.harmonia/epics/<epic-slug>.json` in `gate_reports[<gate-id>]` with `verified_at`, `verifier_agent`, `steps[]`, and `overall_status` (`pass` | `fail` | `partial`).
8. **Pass policy by `verifier`:**
   - `agent-auto`: when all machine-assertable steps pass, recommend pass. Append the gate id to `.harmonia/epics/<epic-slug>.json` `passed_gates` only when the operator explicitly requests auto-pass in this session.
   - `agent-then-human`: report is a pre-flight for human sign-off; highlight UX steps needing operator spot-check. The human records the pass by appending the gate id to `passed_gates`.
   - `human-required`: report is a checklist aid only; never recommend auto-pass. The human records the pass in `passed_gates`.
9. Return control to the parent orchestrator when invoked as a child. When standalone, hand the report to the operator.

Rules:
- Never modify implementation code during verification (readonly session).
- Never append to `passed_gates` unless the operator explicitly requests auto-pass in this session for an `agent-auto` gate.
- Prefer deterministic checks (pytest, curl, file assertions) over ad-hoc agent judgment for `agent-auto` gates.
- When a verify step is ambiguous, fail the step and note how to rewrite it as a machine-assertable sentence.
