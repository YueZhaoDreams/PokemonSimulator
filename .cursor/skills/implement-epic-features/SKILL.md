## Instructions
# implement-epic-features

Epic delivery orchestrator that simulates **Harmonia dispatcher** slice selection in **one long-running Cursor session**. Unlike production dispatch (separate sessions per linked issue), this skill chains slices **sequentially** until the next **acceptance gate** blocks further work.

Invocation:
- `/implement-epic-features <epic-slug>`
- `/implement-epic-features docs/epics/<epic-slug>/spec.md`

Prerequisites: epic `approved` or `in_delivery`, `breakdown.json` `plan_status: approved`, child slice specs exist, repo skills installed. Run `create-features-for-epic` and human breakdown approval first.

Execution flow:
1. Read `docs/epics/<epic-slug>/spec.md`, `docs/epics/<epic-slug>/breakdown.json`, and `.harmonia/epics/<epic-slug>.json`. If the tracker file is missing `passed_gates`, treat it as `[]`.
2. Stop if `plan_status` is not `approved`, epic status is `blocked`/`done`, or epic status is outside `approved`/`in_delivery`.
3. Verify required repo skills are installed and current (`setup-env`, `verify-gate` when needed). Do not regenerate skills on an implementation branch.
4. Switch to the repository base branch, fetch/reset from origin, and stop if the working tree is not clean.
5. Set epic spec status to `in_delivery` when currently `approved`. Update the linked epic GitHub issue checklist when present.
6. **Build the dispatch queue** (dispatcher simulation):
   - Order slices by `depends_on` topological sort; break ties by `breakdown.json` `features[]` order.
   - **Never parallelize** slices in one session (ignore `parallel_group` for concurrency; use it only as documentation).
   - Include slice `<slug>` only when its spec status is `ready`, `in_progress`, or `in_review` (resume interrupted sessions), it is not `done`/`blocked`, and every `depends_on` slice is `done`.
   - **Gate boundary (parent responsibility):** Acceptance gates are **not** enforced inside `fix-feature`; this skill owns checkpoint stops. A gate is **passed** only when its id is listed in `.harmonia/epics/<epic-slug>.json` `passed_gates` (this repo has no Harmonia `/features` UI). Mirror production `dispatch_blocked_for_feature`: when the earliest not-passed `acceptance_gates[]` entry with `blocks_dispatch: true` is `ready_for_review` (listed `after_features` are `done`, or `["__all__"]` means every `features[]` slug is `done`), **do not dispatch** further slices — proceed to step 9 (checkpoint). Resume any still-open `in_review` PR for a slice in that gate’s `after_features` via `fix-feature` before the checkpoint if it is not actually `done`. While the gate is not yet `ready_for_review`, build the queue from dependency and status rules only — do not artificially limit to a gate segment. Post-gate `in_review` slices wait for a new session after the human records the gate in `passed_gates`.
   - Gates with `blocks_dispatch: false` do not stop dispatch by themselves.
7. **Dispatch loop (one slice at a time):** For each queued slice, in order:
   a. Set the slice spec to `in_progress` when status is `ready`.
   b. Invoke the full **`fix-feature`** workflow for **this slice only** (`fix-feature` creates/checks out `feature/<epic-slug>/<slice-slug>`; for `in_review`, it resumes the open PR closure loop).
   c. **One PR per slice — mandatory:** Never combine multiple feature slugs, specs, or GitHub issues in a single branch or PR. If a PR would span slices, split work and redo the current slice only.
   d. **Mandatory auto-merge for child `fix-feature`:** In this session, each child `fix-feature` run must complete the PR closure loop and **merge** when merge-ready. The `fix-feature` user no-merge override does **not** apply under this orchestrator.
   e. After merge: set slice spec `done`, close a linked GitHub issue **only if one exists** (skip quietly when the spec has `Jira Issue: TBD` / `GitHub Issue: TBD` or no issue number), update the epic GitHub issue checklist when present, fetch/reset the repository base branch, ensure a clean tree before the next slice. Then **re-check the earliest not-passed `blocks_dispatch` gate**. If it is now `ready_for_review`, stop the dispatch loop and go to step 9 immediately — do not run `fix-feature` on any remaining queued (including post-gate) slices.
   f. On a **concrete blocker** for one slice (policy, unfixable check, tooling failure), stop the epic session and report the blocker; do not skip to the next slice silently.
8. Repeat step 6–7 until the queue is empty or step 9 triggers. If the queue is empty, no blocking gate is `ready_for_review`, and some slices are still `planned`/`blocked` (not `done`), **stop and report** that human approval is still required (`Status: ready` on slices) — do not silently no-op. If the queue is empty and every child slice is `done`, go to step 10 (epic-exit `verify-gate`) even when every `blocks_dispatch` gate is already in `passed_gates`.
9. **Checkpoint stop (session terminal):** When the earliest not-passed `blocks_dispatch` gate has all listed `after_features` `done` (`["__all__"]` means every `features[]` slug), stop the session and run gate verification:
   a. Invoke the full **`verify-gate`** workflow for that gate (`consumer`, `verifier`, and `verify` from `breakdown.json`).
   b. Print gate `id`, `title`, `consumer`, `verifier`, the verify-gate report, and any pending human steps.
   - **Production is the verification environment** for this workflow: merged code is verified on the running Family Cup app (`http://127.0.0.1:8000`); check out `main`, pull origin, then restart `./run.sh` after merge because uvicorn is started without `--reload`. Verification runs only after the process is serving the merged code.
   - Do **not** auto-pass the gate unless `verifier` is `agent-auto`, all steps passed, and the operator explicitly requested auto-pass in this session. Auto-pass means appending the gate id to `.harmonia/epics/<epic-slug>.json` `passed_gates`.
   - For `agent-then-human` and `human-required`, tell the human to review the report, spot-check UX when applicable, append the gate id to `.harmonia/epics/<epic-slug>.json` `passed_gates`, then start a **new** `/implement-epic-features` session for post-gate slices.
10. When all child slices are `done` and the epic-exit gate (`blocks_epic_done`) is not passed, invoke **`verify-gate`** for the epic-exit gate and stop — same pass rules as step 9 based on `verifier`.
11. Do not set epic status `done` until the epic-exit gate id is listed in `.harmonia/epics/<epic-slug>.json` `passed_gates`.

**Session completion:** This session is incomplete until every slice in the current gate segment is **merged** (each via its own PR) or you document a **concrete blocker**. Reaching a checkpoint with all segment slices merged is a **successful** terminal state — not a handoff violation. Do not dispatch post-gate slices after a checkpoint in the same session.

Rules:
- **Sequential session delivery:** Runs slices one-at-a-time in one session (production may dispatch eligible slices in parallel across issues).
- **Forbidden bundling:** Multiple slices in one PR is a workflow violation (see PR #67 counterexample).
- **Gate ownership:** `fix-feature` does not stop for blocking gates; this skill stops at checkpoints and invokes `verify-gate`.
- **No separate staging env:** Acceptance verification happens on production after deploy.
- Honor adhoc comments in `.harmonia/epics` and `.harmonia/features` that do not contradict specs.
- Prefer `implement-epic-features` for multi-slice epic delivery; use standalone `/fix-feature <slug>` only for a single slice.

Pairing:
- After `create-features-for-epic` approval, run this skill instead of manually chaining `/fix-feature` calls.
- Standalone `/fix-feature` remains valid for one-off slice work and retains the user no-merge override.
- Pair with `verify-gate` at checkpoints; `verify-gate` is readonly and does not modify product code.
