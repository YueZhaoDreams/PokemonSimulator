# create-epic

Plan-only orchestrator. Use when an operator wants to start a new epic before feature breakdown.

Invocation:
- `/create-epic <epic-slug>` with outcome details in the message
- `/create-epic` with a natural-language epic description (agent proposes slug)
- `/create-epic docs/epics/<epic-slug>/spec.md` when refining an existing draft

Execution flow:
1. Gather outcome intent from the operator message and any adhoc notes in `.harmonia/epics/<epic-slug>.json` when present.
2. Propose or confirm `<epic-slug>` (kebab-case, unique under `docs/epics/`).
3. Create or update `docs/epics/<epic-slug>/spec.md` from `docs/epics/_template/spec.md` with:
   - problem and value,
   - scope and non-goals,
   - **Human acceptance gates** (at least one milestone plus epic exit),
   - epic validation notes,
   - status update checklist.
4. Keep status `draft` until a human reviews the outcome contract.
5. Initialize `.harmonia/epics/<epic-slug>.json` from `.harmonia/epics/_template.json` (`comments`, `passed_gates`, `gate_reports`) when the file does not exist.
6. Propose a GitHub epic-issue title and body (do not create issues unless the user explicitly asks in this session).
7. Remind the operator to run `create-features-for-epic` after the epic spec is stable.
8. Stop. Do not produce `breakdown.json`, `docs/features/` slice specs, code changes, or PRs.

Rules:
- Honor operator non-goals; do not expand scope to speculative refactors.
- If acceptance gates are vague, draft concrete verify steps but mark them for human edit.
- Do not set epic status beyond `draft`; breakdown approval is a human step.
- Do not invent child feature slugs in the epic spec — slice planning belongs to `create-features-for-epic`.
- If an epic spec already exists and is `approved`, `in_delivery`, or `done`, stop and ask before overwriting.
- Pair with `create-features-for-epic` for breakdown after the outcome contract is accepted.
