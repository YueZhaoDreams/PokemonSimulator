# compile-test-fix-loop

Goal:
Execute a structured build -> test -> fix loop with clear signal separation, deterministic debugging, and knowledge extraction.

Execution loop:
0. Identify commands
- Detect or infer the compile/build command and the test command.
- If unclear, inspect repo config or call setup-env.
- If the repo truly has no separate compile/build step, record that explicitly before moving on.

1. Compile stage (always first)
- Run the compile/build command first.
- If compile fails, extract the exact errors, identify the affected modules or files, and classify the failure as one of: missing dependency, API mismatch, type or signature error, or build config issue.
- Treat compile failures as their own queue. Do not mix them with later logic fixes.

2. Fix compile errors
- Apply the smallest fix that addresses one root cause.
- Avoid batching unrelated changes.
- Re-run compile immediately.
- Repeat until compile is clean or a clear blocker is identified.

3. Test stage
- After compile is clean, run the narrowest known relevant tests first.
- If no narrower target is known, run the default test suite.
- Capture failing tests, stack traces, and the affected logic path.

4. Root cause analysis (mandatory)
- Before changing code for a test failure, identify what broke, why it broke, and whether the problem is a regression, logic bug, environment issue, or concurrency issue.
- Check historical intent when helpful, including git blame, nearby comments, and related prior fixes.
- Form one hypothesis before editing.

5. Fix test failures
- Apply one minimal fix for the current hypothesis.
- Re-run the same test command immediately.

6. Loop discipline
- If the failure persists, refine the hypothesis using the new evidence.
- If a new failure appears, treat it as the next input instead of making blind edits.
- Never bundle speculative changes across multiple categories.

7. Broad validation
- After targeted tests pass, run the broader required suite.
- Optionally re-run compile/build to confirm the repo remains stable.

Harmonia-specific rules:
- Compile is mandatory before tests.
- Do not skip compile just because tests are available.
- Keep compile failures separate from logic failures.
- Do not mix fixes across compile, test, environment, and concurrency categories unless the evidence forces it.
- If the next safe fix is architectural rather than local, stop and raise or recommend a follow-up Jira refactor issue.

Knowledge extraction (mandatory):
- Classify the resolved issue as compile, test, environment, concurrency, or regression.
- Extract the root-cause pattern and a concrete prevention method.
- Suggest a regression test, catalog entry, or build rule when relevant.

Stopping conditions:
- Compile is clean.
- All required tests pass.
- Or a clear external blocker is identified.

Success criteria:
- Build succeeds or the repo is confirmed to have no separate build step.
- Required tests pass.
- No regression is detected in broader validation.
- Final output includes compile issues if any, root cause, fix, commands run, and a prevention suggestion.

PokemonSimulator runtime (operators):
- This repo has no separate compile/build step beyond Python bytecode compile. Use `.venv/bin/python -m compileall -q app tests`.
- After Python changes, run `.venv/bin/pytest -q` from the repo root.
- Printed card text is the engine source of truth: attacks go through `parse_effects(text)` and abilities through `parse_ability_effects(text)`. Do not hardcode look-N sizes into `app/engine/game.py`.
